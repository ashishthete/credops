# OpsDeck Phase 10a: Hub core, Microsoft SSO and roles Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

Phase 10 is split in two. This plan, **10a**, builds the Hub server core, Microsoft
Entra sign-in, the admin and maintainer roles, and groups and grants. It also
connects the desktop app to the Hub and enforces `DeployAccess`.
**10b** (`2026-10-19-phase10-hub-10b.md`) adds the server runner, shared deploy
secrets, env locks, team history and live status. 10b starts only after 10a is
merged. The "Upstream interfaces" section below applies to both plans.

**Goal:** A self-hosted OpsDeck Hub that knows who you are through Microsoft
Entra ID and decides, on the server, what you may deploy:
- **Hub server.** A small Node 24 service in a new `hub/` package. It uses
  Fastify over HTTP, keeps its data in SQLite through `node:sqlite`, and keeps
  its own hash-chained audit.
- **Sign-in.**
  - The desktop app is an Entra public client. It signs in with authorization
    code + PKCE in the system browser and catches the redirect on a loopback
    port.
  - The Hub validates the Entra access token (signature, issuer, audience,
    tenant, scope and expiry), then issues its own opaque session token.
  - The desktop app keeps that session token, and the Entra refresh token,
    with `safeStorage`.
- **Roles.**
  - **Admin:** manages users, groups and grants; can deploy everywhere; can
    break locks.
  - **Maintainer:** deploys only where one of their groups grants access.
- **Groups.**
  - A built-in **Default** group grants all environments and can't be deleted.
  - Other groups get grants scoped to all environments, one environment, or
    one deployment in one environment.
  - Every user must be in a group. A user who has signed in but belongs to no
    group is *pending* and sees nothing.
  - The first admin comes from the Hub config and is put in Default on their
    first sign-in.
- **Client.**
  - A **Hub** section lets the user connect to a Hub URL, sign in, see their
    role and groups, and, as an admin, manage people, groups, grants and the
    Hub audit.
  - `HubAccess` implements Phase 8's `DeployAccess`, and `RoutingAccess` sends
    Hub-linked environments to it. Locally, everything stays allow-all.

**Architecture:**
- **`hub/`** is a separate package with its own `package.json`, `tsconfig.json`,
  `vitest.config.mts` and `vite.config.mts`. It is not part of the pnpm
  workspace. It reuses repo code by relative import:
  - **Shared contract.** `src/shared/hub.ts` holds the Hub API types and
    constants. It is type-only plus plain constants, so the desktop app's
    main process, its renderer and the Hub all import it.
  - **Pure helpers from main.** The Hub imports `redact`
    (`src/main/security/redact.ts`), `canonicalJson`/`GENESIS_HASH`
    (`src/main/audit/audit-log.ts`), and, in 10b, `seal`/`openSealed`
    (`src/main/vault/crypto.ts`) and `generateEd25519`
    (`src/main/vault/openssh.ts`). None of them import Electron.
- **Server modules:**
  - `config.ts` loads and validates the JSON config;
  - `db.ts` opens SQLite and runs the Hub's own migrations;
  - `audit.ts` is the Hub audit chain;
  - `auth/entra.ts` validates tokens with `jose`;
  - `auth/sessions.ts` holds Hub sessions;
  - `access/directory.ts` holds users, groups, members and grants;
  - `access/policy.ts` has the pure `decide()`;
  - `routes/*.ts` are thin Fastify route files;
  - `app.ts` wires them into `buildApp(deps)`, which tests drive through
    `app.inject()`.
- **Client modules** live under `src/main/hub/`:
  - `oidc.ts`: PKCE, the loopback receiver, code exchange and refresh. These
    are hand-rolled over `fetch` and `node:crypto`; see Decisions;
  - `client.ts`: `HubClient`, a fetch wrapper that refreshes the session once
    on a 401;
  - `connection.ts`: `HubConnection`, the link, sign-in state and
    `safeStorage` tokens;
  - `access.ts`: `HubAccess` and `RoutingAccess`.

  IPC goes in `src/main/ipc/handlers/hub.ts`, and the renderer gets
  `src/renderer/src/hub/` plus `pages/hub/`.
- **Tests never leave localhost.**
  - `tests/main/fake-entra.ts` is an in-process OIDC issuer on `127.0.0.1:0`.
    It serves discovery, JWKS, authorize (auto-consent, 302 to the loopback)
    and token (PKCE-checked, refresh rotation), and signs RS256 with
    `node:crypto`.
  - The Hub and the client both test against it. Nothing calls
    `login.microsoftonline.com`.

**Tech Stack:**
- Phases 1–9.
- **The Hub runs on Node ≥ 24** (`node:sqlite`, global `fetch`) with three
  new dependencies, all in `hub/package.json` only:
  - **`fastify@5`:** routing, JSON-schema body validation and `inject()` for

## Decisions (made here; the controller should know)

1. **The Hub stack is Node 24, Fastify 5, `node:sqlite` and `jose`.**
   - **SQLite, not Postgres.** The Hub serves one team from one VM (§8.9 "an
     existing Azure VM"). `node:sqlite` is already the app's engine, so there
     is no native build, it backs up as one file, and the migration and
     transaction helpers are the ones we already have. Writes are tiny (runs,
     events, audit), and WAL handles a few concurrent readers. If the Hub ever
     needs HA, Postgres is a later swap behind the same stores.
   - **Fastify** brings JSON-schema validation, `inject()` (socket-free
     tests), hooks for auth, and pino logging with header redaction.
   - **Live status is SSE, not WebSocket** (10b). It is one-way
     server-to-client, an `Authorization` header works with plain `fetch`
     (Node's `WebSocket` can't set headers), it needs no extra dependency, and
     reconnect plus backfill is simple.
2. **The client OIDC is hand-rolled (about 200 lines), not MSAL Node.** The
   spec mentions MSAL Node, but MSAL refuses non-`https` authorities
   (`authority_uri_insecure`). That makes the binding "local fake issuer"
   test rule impossible without TLS fakery in tests.
   - Code + PKCE (S256), loopback and refresh are standard RFC 6749/7636/8252
     over `fetch`.
   - In production the authority is pinned to
     `https://login.microsoftonline.com/<tenant-guid>/v2.0`.
   - Plain-`http` authorities and Hub URLs are accepted **only** for
     `127.0.0.1`/`localhost`, which is what tests use.
3. **The Hub validates an Entra *access token* for its own API, not the
   id_token.**
   - It needs `aud ∈ {clientId, api://clientId}`, `iss` =
     `https://login.microsoftonline.com/<tenant>/v2.0`, `tid` = the tenant,
     `scp` ∋ `access_as_user`, RS256 only, and 120 s of clock skew.
   - An id_token has no `scp`, so it is rejected.
   - The Hub then issues its **own opaque session**: 32 random bytes, stored
     as SHA-256, 12 h by default. Revoking is a row delete, and every role or
     group change applies on the next request, because nothing is cached in a
     token.
4. **Every user must be in a group, and 10a enforces it.**
   - Pending is derived: an enabled user with zero memberships.
   - Removing someone's **last** membership is refused with `409 last_group`
     "Every user must be in a group. Add <name> to another group first, or
     disable them." Deleting a group that is someone's last group is refused
     the same way.
   - Demoting or disabling the **last enabled admin** is refused with
     `409 last_admin`.
   - "Add all pending people to Default" is one bulk call, to cover "to start,
     the admin adds everyone to Default".
5. **Grant attribution is narrowest-first.**
   - When several groups allow an action, the audit's `via` names the
     narrowest grant: deployment, then environment, then all. Ties go to the
     oldest group.
   - Admin actions record `via: role admin`.
6. **Hub environment and deployment ids are the publishing admin's local
   UUIDs** (10b). 10a validates only that grant ids are UUID-shaped. 10b
   checks that they exist in the registry and drops their grants on
   unpublish.
7. **TLS.** The Hub listens on `127.0.0.1:8787` by default, behind a TLS
   proxy (Caddy) on the VM. A non-loopback `listen.host` requires
   `tls.certFile`/`tls.keyFile` in the config, or the Hub refuses to start.
   Clients refuse a non-`https` Hub URL unless its host is loopback.

## Global Constraints

- **All Phase 1–9 constraints still hold:**
  - the window flags and CSP;
  - the renderer imports no Node;
  - modules under test import only *types* from `electron`;
  - every IPC channel has a validator, and validator errors name the path,
    never the value;
  - mutations call `vault.assertUnlocked()`;
  - audit is appended after COMMIT;
  - renderer mutations go through `attempt(...)`;
  - earlier migrations are never edited;
  - stores take `{ db, audit, vault, now?, ids? }`.
- **Commands** (`node_modules` is a symlink, so `pnpm test` isn't used):
  - **App tests:** `./node_modules/.bin/vitest run [files]`.
  - **App typecheck:** `./node_modules/.bin/tsc --noEmit -p tsconfig.node.json && ./node_modules/.bin/tsc --noEmit -p tsconfig.web.json`.
  - **Hub tests:** `./node_modules/.bin/vitest run --config hub/vitest.config.mts [files]`.
  - **Hub typecheck:** `./node_modules/.bin/tsc --noEmit -p hub/tsconfig.json`.
  - **Hub dependencies:** `~/Library/pnpm/bin/pnpm --dir hub install --ignore-workspace`,
    which creates a real `hub/node_modules` (gitignored). **This needs the
    network once.** If the sandbox blocks it, the controller runs it. If pnpm
    touches `pnpm-workspace.yaml`, run `git checkout pnpm-workspace.yaml`.
  - The root vitest config is not changed. Hub tests run only through the Hub
    config.
- **No secret in plaintext anywhere.** That covers Entra tokens, Hub session
  tokens, refresh tokens, authorization codes and PKCE verifiers.
  - They never appear in logs, audit (Hub or local), error messages, IPC
    results (except the token-free `HubStatus`), the renderer or the local
    DB.
  - The local DB holds tokens only as `safeStorage` ciphertext.
  - The Hub stores only `sha256(sessionToken)`.
  - **Pino:**
    - `redact: ['req.headers.authorization', 'req.headers.cookie']`;
    - the request serializer logs `method`, the path without its query
      string, and `remoteAddress`;
    - bodies are never logged.
  - **Hub error responses** are
    `{ error: HubErrorCode, message: string }`. The message is fixed text,
    run through `redact(message, knownSecrets())`. A 500 says
    `Internal error` and logs only `err.name` and a redacted message.
- **Localhost-only tests:** `127.0.0.1:0` sockets or `app.inject()`. There is
  no DNS, no `login.microsoftonline.com`, no real `~/.ssh`, no
  `SSH_AUTH_SOCK` and no real browser. `openBrowser` is a dep, and tests use
  a `fetch`-driven fake browser.
- **Limits** (`src/shared/hub.ts`):
  - `SESSION_TTL_HOURS = 12` (config range 1–72);
  - `SIGN_IN_TIMEOUT_MS = 300_000`;
  - `HUB_TIMEOUT_MS = 15_000`;
  - `ACCESS_CACHE_MS = 30_000`;
  - `MAX_GROUPS = 200`, `MAX_GRANTS_PER_GROUP = 500`;
  - `GROUP_NAME = /^[\p{L}\p{N} ._-]{1,64}$/u`, `MAX_GROUP_DESCRIPTION = 280`;
  - `HUB_BODY_LIMIT = 1_048_576`;
  - `MAX_BULK_MEMBERS = 500`.
- **Desktop migration 9 (`hub`)**, verbatim:
  ```sql
  CREATE TABLE hub_link(id INTEGER PRIMARY KEY CHECK (id = 1),
    url TEXT NOT NULL, hub_id TEXT NOT NULL, hub_name TEXT NOT NULL,
    user_oid TEXT, user_upn TEXT, user_name TEXT,
    session_enc BLOB, session_expires_at TEXT, refresh_enc BLOB,
    linked_at TEXT NOT NULL, updated_at TEXT NOT NULL,
    CHECK ((session_enc IS NULL) = (session_expires_at IS NULL)));
  CREATE TABLE hub_env_links(
    environment_id TEXT PRIMARY KEY REFERENCES environments(id) ON DELETE CASCADE,
    hub_id TEXT NOT NULL, published_at TEXT NOT NULL, manifest_hash TEXT NOT NULL);
  ```
  `hub_env_links` is written only by 10b. 10a reads it in `RoutingAccess`.
- **Hub migration 1 (`core`)**, verbatim, in `hub/src/db.ts`:
  ```sql
  CREATE TABLE hub_meta(key TEXT PRIMARY KEY, value TEXT NOT NULL);
  CREATE TABLE users(oid TEXT PRIMARY KEY, tid TEXT NOT NULL, upn TEXT NOT NULL, name TEXT NOT NULL,
    role TEXT NOT NULL CHECK (role IN ('admin','maintainer')),
    disabled INTEGER NOT NULL DEFAULT 0 CHECK (disabled IN (0,1)),
    created_at TEXT NOT NULL, last_seen_at TEXT);
  CREATE TABLE sessions(token_hash TEXT PRIMARY KEY,
    oid TEXT NOT NULL REFERENCES users(oid) ON DELETE CASCADE,
    created_at TEXT NOT NULL, expires_at TEXT NOT NULL);
  CREATE INDEX sessions_oid ON sessions(oid);
  CREATE TABLE groups(id TEXT PRIMARY KEY, name TEXT NOT NULL COLLATE NOCASE UNIQUE,
    description TEXT NOT NULL DEFAULT '', builtin INTEGER NOT NULL DEFAULT 0 CHECK (builtin IN (0,1)),
    created_at TEXT NOT NULL, updated_at TEXT NOT NULL);
  CREATE TABLE group_members(group_id TEXT NOT NULL REFERENCES groups(id) ON DELETE CASCADE,
    oid TEXT NOT NULL REFERENCES users(oid) ON DELETE CASCADE,
    added_at TEXT NOT NULL, added_by TEXT NOT NULL, PRIMARY KEY (group_id, oid));
  CREATE INDEX group_members_oid ON group_members(oid);
  CREATE TABLE grants(id TEXT PRIMARY KEY, group_id TEXT NOT NULL REFERENCES groups(id) ON DELETE CASCADE,
    scope TEXT NOT NULL CHECK (scope IN ('all','environment','deployment')),
    environment_id TEXT, deployment_id TEXT, created_at TEXT NOT NULL,
    CHECK ((scope = 'all') = (environment_id IS NULL)),
    CHECK ((scope = 'deployment') = (deployment_id IS NOT NULL)));
  CREATE UNIQUE INDEX grants_unique ON grants(group_id, scope, IFNULL(environment_id,''), IFNULL(deployment_id,''));
  CREATE TABLE audit(id INTEGER PRIMARY KEY AUTOINCREMENT, ts TEXT NOT NULL,
    actor_oid TEXT, actor_upn TEXT, actor_name TEXT, actor_role TEXT, via_group TEXT,
    action TEXT NOT NULL, target_type TEXT, target_id TEXT, target_label TEXT,
    outcome TEXT NOT NULL, details TEXT NOT NULL, prev_hash TEXT NOT NULL, hash TEXT NOT NULL);
  CREATE TRIGGER groups_builtin_keep BEFORE DELETE ON groups WHEN OLD.builtin = 1
    BEGIN SELECT RAISE(ABORT, 'builtin group'); END;
  CREATE TRIGGER grants_builtin_keep BEFORE DELETE ON grants
    WHEN (SELECT builtin FROM groups WHERE id = OLD.group_id) = 1
    BEGIN SELECT RAISE(ABORT, 'builtin group'); END;
  CREATE TRIGGER audit_no_update BEFORE UPDATE ON audit BEGIN SELECT RAISE(ABORT, 'audit is append-only'); END;
  CREATE TRIGGER audit_no_delete BEFORE DELETE ON audit BEGIN SELECT RAISE(ABORT, 'audit is append-only'); END;
  ```
  The same migration then seeds the Default group and its grant, using the

## Review Focus

1. **Token confusion and forgery.** Each of these gets `401 unauthenticated`
   and a `session.denied` audit with a reason code, never the token: an Entra
   token for another audience, another tenant or another issuer; an id_token;
   an expired token; one signed by an unknown key; `alg: none`; and an HS256
   token "signed" with the public JWK.
   *Pinned:* Task 3 `rejects every forged or misdirected token`.
2. **Stale authorization.** A maintainer is removed from their only granting
   group, or disabled, while their session is live. Their very next `/access`
   or admin call reflects that, with no cached grant in a token.
   *Pinned:* Task 5 `authorization changes apply on the next request`.
3. **The "every user in a group" invariant under every path.** It must hold
   when someone removes a last membership, deletes a group that is someone's
   last group, bulk-removes members, tries to delete Default or its grant
   (even by raw SQL), or demotes or disables the last admin.
   *Pinned:* Task 5 `the group invariant holds on every path`, and Task 1
   `default group and its grant survive a raw delete`.
4. **The loopback receiver under hostile or messy input.** These all fail
   cleanly with the port closed and no code or verifier in an error or log: a
   wrong `state`, an `error=access_denied` redirect, a hit on another path, a
   second hit after success, a timeout, and a Cancel.
   *Pinned:* Task 6 `loopback rejects bad state, other paths and late hits`
   and `cancel and timeout close the port`.
5. **Tokens at rest and in transit inside the app.**
   - `safeStorage` unavailable means sign-in is refused before the browser
     opens, and nothing is stored.
   - `hub:status` never carries a token.
   - A Hub 500 whose text includes the session token reaches the renderer
     redacted.
   - The `hub_link` row holds no token plaintext, which is checked by
     scanning the DB bytes.

   *Pinned:* Task 7 `refuses sign-in without keychain`, `status and errors
   never carry tokens` and `db file holds no token plaintext`.

  ```ts
    | { allowed: true; via: { role: HubRole; groupId: string | null; groupName: string | null } }
    | { allowed: false; code: HubDenyCode; reason: string }
  ```
- **`decide(user: HubUser, groups: HubGroup[], action: HubAction, target?: AccessTarget): HubDecision`.**
  It is pure, in this order:
  1. `disabled` gives `disabled`, `Your Hub account is disabled`.
  2. `pending` gives `pending`,
     `You're not in any group yet. Ask a Hub admin to add you.`
  3. `admin`, `deploy.edit` (publishing, 10b) and `lock.break` need the
     admin role, otherwise `admin_only`, `Only Hub admins can do this`.
  4. An admin is allowed, with `via { role: 'admin', groupId: null }`.
  5. Otherwise the action is allowed if any of the user's groups has a
     matching grant:
     - `all`;
     - `environment` whose id equals `target.environmentId`;
     - `deployment` grants: **every** id in `target.deploymentIds` must be
       covered by a deployment grant in that environment (or a wider grant).
       With no `deploymentIds`, a deployment grant matches only for
       `deploy.view`, so a maintainer sees the environment in the catalog.
  6. `via` is the narrowest single grant that covers the whole target
     (deployment, then environment, then all); ties go to the oldest group
     by `createdAt`. When no single grant covers it all but the union
     does, the action is allowed with
     `via { groupId: null, groupName: 'multiple' }`, and the per-deployment
     groups go in `details.vias` when it is audited.
  7. Nothing matches: `no_grant`,
     `You don't have access to <target>. Ask a Hub admin for a grant.`
     The target is the deployment or environment id. The client swaps in
     names.

  `deploy.view`, `release.start`, `release.rollback`, `release.cancel` and
  `env.lock` all use the same grant check.
- **`Directory`** (groups part). Each method audits and runs inside
  `inTransaction` (import `src/main/db/tx.ts` if it is generic over `Db`,
  else a 6-line local copy):

  ```ts

    | 'denied' | 'exchange' | 'refresh_expired' | 'network'
  export class OidcError extends Error { code: OidcErrorCode }   // fixed messages, never a code/verifier/token
  export interface OidcEndpoints { issuer: string; authorizationEndpoint: string; tokenEndpoint: string }
  export interface TokenSet { accessToken: string; refreshToken: string | null; expiresAt: number }
  export function checkAuthority(authority: string): URL
  export function discover(authority: string, deps: { fetch: typeof fetch }): Promise<OidcEndpoints>
  export function pkce(): { verifier: string; challenge: string }
  export function startLoopback(opts: { path: string; state: string; timeoutMs: number; signal: AbortSignal; host?: '127.0.0.1' | 'localhost' }):
    Promise<{ redirectUri: string; code: Promise<string>; close(): void }>
  export function authorizeUrl(ep: OidcEndpoints, cfg: HubMeta['entra'], p: { redirectUri: string; state: string; challenge: string }): string
  export function exchangeCode(ep: OidcEndpoints, cfg: HubMeta['entra'], p: { code: string; verifier: string; redirectUri: string }, deps: { fetch: typeof fetch; now: () => number }): Promise<TokenSet>
  export function refreshTokens(ep: OidcEndpoints, cfg: HubMeta['entra'], refreshToken: string, deps: { fetch: typeof fetch; now: () => number }): Promise<TokenSet>
  export function signIn(cfg: HubMeta['entra'], deps: { fetch: typeof fetch; openBrowser: (url: string) => Promise<void>; signal: AbortSignal; now: () => number; timeoutMs?: number }): Promise<TokenSet>
  ```
- **The rules:**
  - `checkAuthority` accepts `https://login.microsoftonline.com/<guid>/v2.0`
    or `http://127.0.0.1|localhost:<port>/<guid>/v2.0`. Anything else gives
    `config`, `The Hub's sign-in authority is not Microsoft Entra`.
    `discover` also requires `issuer` to equal the authority.
  - `pkce()` returns a verifier of 32 random bytes as base64url and an S256
    challenge. `state` is 16 random bytes as base64url.
  - **The loopback:**
    - it listens on `127.0.0.1:0`;
    - the redirect URI is the `cfg.redirectUri` template with the actual
      port, e.g. `http://127.0.0.1:53121/callback`, and its host is taken
      from the template;
    - only `GET <path>` counts, and any other request is a 404;
    - the first hit with a matching `state` resolves the code, replies
      `200 text/html` "Signed in to OpsDeck. You can close this tab." with
      `Cache-Control: no-store`, and closes the server;
    - a mismatched state gives `state_mismatch`;
    - `error=…` gives `denied` (the code only, never `error_description`);
    - a timeout gives `timeout`, and an abort gives `cancelled`;
    - every outcome closes the port.
  - **The authorize URL** carries `client_id`, `response_type=code`,
    `redirect_uri`, `scope` (space-joined `cfg.scopes`), `state`,
    `code_challenge`, `code_challenge_method=S256` and
    `prompt=select_account`.
  - **The token POST** is form-encoded with `client_id`, and has no client
    secret (public client).
  - `expiresAt = now + expires_in·1000 − 60_000`.
  - A 400 `invalid_grant` on refresh gives `refresh_expired`.
