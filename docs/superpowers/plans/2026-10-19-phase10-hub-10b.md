# OpsDeck Phase 10b: Hub runner, shared secrets, env locks and live status Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Depends on 10a** (`2026-10-19-phase10-hub.md`), which is merged first, and
on Phases 8 and 9, which are rebased in first. **10a's "Upstream interfaces",
"Decisions", "Global Constraints" and "Needs real infrastructure" sections
apply here unchanged.** This plan adds to them.

**Goal:** Team deployments run **on the Hub**. In detail:
- **Publishing.** An admin publishes an environment from their own OpsDeck:
  its hosts (address, port, user, jump chain and pinned host keys), its
  deployments and its integrations.
- **Secrets.** The admin uploads the deploy secrets that environment needs.
  The Hub generates a per-environment deploy key, and the admin installs its
  public key on the hosts.
- **Releasing.** Any user whose groups grant the environment opens the
  normal Phase 8 release wizard. Preflight, the release, rollback,
  versioning, notifications and release notes all run on the Hub, using
  Phase 8's own `ReleaseService` and `LocalRunner` server-side.
- **Locks.** Each environment has a lock. Only one release runs at a time,
  and an optional manual "freeze" can hold it.
- **Live status.** Everyone with access sees team-wide history and live
  status through a server-sent-events feed.
- **Secret handling.** Secrets are encrypted at rest with a Hub master key,
  never returned by any API, and never sent to clients.

**Architecture:**
- **Hub** (`hub/src/`):
  - `registry.ts`: the published environments, hosts and deployments;
  - `secrets/keyring.ts` and `secrets/store.ts`: the master key, the sealed
    secrets and the deploy keys;
  - `locks.ts`: the environment locks;
  - `releases/adapters.ts`: the Phase 8 `ReleaseService` deps backed by
    Hub stores;
  - `releases/service.ts`: builds one `ReleaseService` for the process and
    wraps the start, lock and confirm ordering;
  - `routes/releases.ts`, `routes/registry.ts`, `routes/secrets.ts`,
    `routes/locks.ts` and `routes/live.ts`;
  - `live/bus.ts`, the per-user filtered fan-out;
  - `notify/finalize.ts`: Phase 9's `createFinalizeSteps`, wired to Hub
    secrets.
- **Client** (`src/main/hub/`):
  - `publish.ts`: builds an environment manifest from local stores and
    uploads its secrets;
  - `catalog.ts`: the Hub environments this user can see, held in memory
    only;
  - `runner.ts`: `HubRunner`, which implements Phase 8's `ReleaseOps`
    against the Hub, and `RoutingReleases`, which picks the local service or
    the Hub per call;
  - `live.ts`: `LiveFeed`, the SSE consumer with backoff and lossless
    backfill. It re-emits on the existing `deploy:event` and `release:state`
    channels, so **Phase 8b's UI renders Hub releases unchanged**.
- **The renderer** gets catalog environments in Deployments, lock badges and
  freeze, and the Hub admin panels for Environments and Secrets. It also
  gets the grant pickers that 10a left as "All environments" only.

**Tech Stack:** 10a, plus these:

  - `@anthropic-ai/sdk@0.131.0`, the same as Phase 9.
- **Hub binaries:** `ansible-playbook` (ansible-core ≥ 2.14), `ssh-agent`

## Decisions (10b; the controller should know)

1. **The Hub reuses Phase 8's `ReleaseService` and `LocalRunner` instead of
   re-implementing orchestration.** It needs the three seam follow-ups S1–S3
   listed in 10a's Upstream section, all type-only or additive, in Task 4
   Step 1.
2. **The client swaps at the `release:*` surface.**
   - The Hub always builds the `DeployPlan` from **its own registry**.
     Clients send ids only: an environment, deployments, branches, the bump,
     options and the confirm. So no client can redirect a run to another
     host, path or key.
   - That is why `HubRunner` implements `ReleaseOps` (the public surface of
     `ReleaseService`) and not `DeployRunner.start(plan, secrets)`.
3. **Registry ids are the publishing admin's local UUIDs** for environments,
   hosts, deployments and apps. Re-publishing replaces the manifest
   atomically. Phase 8 already uses UUIDv7 for releases, so the ids can't
   collide across machines.
4. **Secret identity.**
   - A Hub secret's id **is the local vault secret id** that the published
     `envTemplate` `${secret:<uuid>}` and `becomeSecretId` refer to. That
     way Phase 8's `secretRefs` resolve on the Hub with no rewriting.
   - Integration secrets (a Teams webhook per environment; global SendGrid,
     GitHub and Anthropic keys) get fixed names, so they need no ids.
   - The admin uploads values from their unlocked vault. The value crosses
     TLS once, in main only. The renderer never sees it.
5. **Secrets at rest.**
   - **Algorithm.** AES-256-GCM via the app's
     `seal(key, plaintext, aad)`/`openSealed`.
   - **Master key.** 32 bytes from `masterKeyFile` (mode `0600`, owned by
     the Hub user) or `OPSDECK_HUB_MASTER_KEY` (base64), never in the
     config JSON.
   - **AAD.** `hub-secret:v1:<id>:<environmentId|*>:<name>`. A ciphertext
     moved to another row fails to open.
   - **Sentinel.** A sealed sentinel in `hub_meta` refuses boot on a wrong
     key: `master key does not match this database`.
   - **Key id.** `key_id` is stored for a future rotation (deferred).
   - **No read path.** **No API returns a value**; the routes are
     write-only.
6. **Where plaintext exists, and only there:**
   - in Hub process memory during a release, in the `RunSecrets` that
     `ReleaseService` holds from start to finish and then drops (Phase 8
     already tests this);
   - in Ansible's environment (`OPSDECK_SECRETS`, the Phase 8 mechanism);
   - in the target host's `.env`, which is the point of `managedEnv`;
   - deploy keys only in the run's private `ssh-agent`.

   It is redacted by Phase 8's translator and by the Hub's
   `knownSecrets()` everywhere else: events, audit, errors, logs, Teams and
   SSE.
7. **One Hub deploy key per environment** (ed25519, generated on the Hub).
   Published hops are forced to `auth: 'key'`, using that key. Admins
   install the public key on each target and jump host
   (`authorized_keys`), and the UI shows it with a copy button. Hub-run
   releases never use any person's key.
8. **Host keys are pinned, with no TOFU on the Hub.** The publisher's
   `KnownHostStore` entries for every hop (public keys only) ship in the
   manifest. The Hub's `verify` accepts only those. An unknown or changed
   key blocks preflight with `Host key for <label> isn't pinned on the Hub.
   Re-publish <env> after connecting to it once from OpsDeck.`
9. **Environment lock.**
   - **Release lock.** Taken atomically (`INSERT` into `env_locks`, PK
     `environment_id`, inside `BEGIN IMMEDIATE`) at preflight, and held
     until the release is terminal or discarded. This sits in front of
     Phase 8's own "one active per environment" rule.
   - **Manual freeze.** Optional, with a reason and an expiry: 4 h by
     default, 24 h at most. It blocks everyone except its holder. The
     holder or an admin can lift it; an admin lifting someone else's needs
     the typed environment name when the environment is protected, and it
     is audited.
   - **Contention.** A blocked user gets `409 env_locked` naming the
     holder.
   - **Restart.** Release locks are cleared, and `failInterrupted()` marks
     the releases they held as failed.
10. **Live status uses SSE.** Each message is filtered **per message** by
    `decide(deploy.view)` against the DB, so a revoked grant stops events at
    once. A disabled user's or revoked session's stream is closed.
11. **Notifications run once, on the Hub.**
    - Phase 9's local dispatcher subscribes only to the **local**
      `ReleaseService.onEvent`, so Hub releases never double-post.
    - The client shows a macOS notification only for Hub releases the user
      started.
12. **The client caches only in memory.** The catalog, Hub releases and
    events are never written to the local DB, so the "client caches" rule
    holds. The only Hub rows on disk are the 10a `hub_link` and
    `hub_env_links`.

## Review Focus

1. **Secret leaks.** One sentinel value (`HUBSECRET-<random>`) is set as an
   env secret and a Teams webhook. A full release then runs: it fails, rolls
   back and fires a notification. The sentinel must appear in **none** of
   these:
   - the `hub.db` and `-wal` bytes;
   - captured pino output and every HTTP response body;
   - every SSE frame and every audit row;
   - the Teams payload, apart from the webhook URL that is posted to;
   - the client's local DB and IPC payloads.

   *Pinned:* Task 2 `no secret plaintext at rest or in any response`, and
   Task 4 `a release leaks no secret anywhere`.
2. **Concurrent starts.** Ten parallel preflights on one environment:
   exactly one gets `201`, nine get `409 env_locked` naming the holder, and
   `env_locks` holds one row.
   *Pinned:* Task 3 `exactly one concurrent acquire wins`, and Task 4
   `parallel preflights: one wins`.
3. **A Hub restart mid-release.** On boot, the release is `failed` with
   `Hub restarted`, its release lock is gone, a new preflight works, and
   the audit chain verifies.
   *Pinned:* Task 4 `restart fails interrupted releases and frees locks`.
4. **The protected confirm through the raw API.** A start with no
   `typedName`, or with `PROD` for `prod`, gets `400 confirm_required`.
   That happens **before** the lock is checked and before
   `ReleaseService.start` is called (the spy has zero calls), and it is
   audited `access.denied`. The same holds for an admin lifting a freeze on
   a protected environment.
   *Pinned:* Task 4 `protected start needs the exact typed name before anything runs`.
5. **Live feed correctness.**
   - A drop mid-release and a reconnect backfill to exactly the persisted
     sequence, with no duplicate ids and no gaps.
   - Removing a user's grant mid-stream stops their frames for that
     environment on the next message.
   - Disabling the user closes their stream.

   *Pinned:* Task 6 `revoked access stops frames immediately`, and Task 7
   `reconnect backfills without duplicates`.

**Interfaces:**
- **`loadMasterKey({ file?, env? }): Buffer`.** It reads 32 bytes
  (base64 in the file or env var).
  - A file whose mode is not `0600` or `0400` gives
    `masterKeyFile must be chmod 600`.
  - A wrong length gives `master key must be 32 bytes (base64)`.
  - Neither source gives `no master key: set masterKeyFile or OPSDECK_HUB_MASTER_KEY`.
- **`KeyRing`:**
  - `new KeyRing(db, key)` checks or creates the `hub_meta('key_check')`
    sentinel;
  - `seal(plain, aad)` and `open(blob, aad)`;
  - `keyId = sha256(key)[0..8]` as hex.
- **`SecretStore`:**
  - `set({ id?, environmentId, name, kind, value }, actor)`, where `id`
    defaults to `uuidv7()` and integration kinds use fixed names;
  - `meta(environmentId?)`, which returns
    `{ id, environmentId, name, kind, updatedBy, updatedAt }[]`;
  - `delete(id)`;
  - `resolveForRun(ids: string[]): Map<id, string>`, used only by T4's
    adapter;
  - `integration(environmentId, kind): string | null`, used only by T5.
- **`DeployKeys`:**
  - `create(environmentId)` uses `generateEd25519('opsdeck-hub:<env name>')`
    and stores `private_enc` sealed with AAD
    `hub-deploykey:v1:<environmentId>`;
  - `publicKey(environmentId)` returns `{ publicKey, fingerprint } | null`;
  - `privateForRun(environmentId): string`, used only by T4.
- **Routes** (admin, through `decide('admin')`):
  - `GET /api/v1/admin/secrets?environmentId=`, which returns metadata
    plus, per environment, `missing: { secretId, name }[]` computed from
    `requiredSecrets`;
  - `PUT /api/v1/admin/secrets/:id` with
    `{ environmentId: string | null, name, kind, value }`. The value is at
    most `MAX_SECRET_BYTES`. It replies `204`, never echoing the value;
  - `DELETE /api/v1/admin/secrets/:id`;
  - `POST /api/v1/admin/environments/:id/deploy-key`, which creates or
    rotates the key and returns `{ publicKey, fingerprint }`;
  - `GET /api/v1/admin/environments/:id/deploy-key`.

  These audit `secret.set`, `secret.delete` and `deploykey.create`, with
  names only.
- **Fastify** gets a `preSerialization` guard on `/admin/secrets*` that
  throws if a response object has a `value` key. That is a belt and braces
  check, and there is a test for it.
