# SSO Login Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** OpsDeck opens only after a Microsoft (Entra, through the Hub) sign-in, or a recent one, for the bound
user. The vaults are then unlocked with Touch ID, a PIN or an optional master password. At least one of Touch
ID or PIN is mandatory.

**Architecture:**

- The main process enforces everything.
  - A new `SsoGate` (`src/main/auth/sso-gate.ts`) turns `HubConnection` results and an `sso_binding` row into
    a verdict.
  - `VaultService` refuses every unlock path unless that verdict allows it.
- The KEK becomes stable:
  - for new setups it is random, and is wrapped separately by the password (optional), the Touch ID Keychain
    cache, and a PIN wrap (scrypt of PIN plus a Keychain pepper);
  - legacy password-derived KEKs keep working and convert on the next password change.
- The renderer gate grows Hub-address and Microsoft steps, plus a three-tab method chooser.

**Tech Stack:**

- Electron 44 (`safeStorage`, `systemPreferences.promptTouchID`)
- React 19, TypeScript
- `node:sqlite` and `node:crypto` (scrypt, AES-GCM through `src/main/vault/crypto.ts`)
- Vitest with Testing Library
- The existing Fastify Hub test fixture (`tests/main/hub-fixture.ts`, localhost only)

**Spec:** `.superpowers/sdd/sso-login-design.md`. It includes the
binding "Product-owner answers (2026-10-21, binding)" at its end, which override §3 and decision 6.

## Global Constraints

- No new dependencies (app or hub).
- No token, PIN, password, pepper or key in plaintext on disk, in logs, audit, IPC payloads or error messages.
  Error texts are fixed strings.
- Tests never touch the real Keychain, real Touch ID, the network beyond localhost, or real Entra. Fake every
  dep: the `QuickUnlockDeps` fakes in `tests/main/quick-unlock.test.ts`, `fakeKeychain` and `testHub()` in
  `tests/main/hub-connection.test.ts`.
- Migrations are additive only.
- The SSO migration lives in one file, `src/main/db/sso-migration.ts`, with `SSO_N` as its version. The
  controller sets `SSO_N` to the next free number at implementation time. Migration 12 is reserved by
  `regions`, and playbook-ops takes the numbers after it.
- Audit stores counts, ids, modes and reasons only: never a token, PIN, password or UPN outside the existing
  `targetLabel` convention.
- Constants:
  - `OFFLINE_GRACE_HOURS = 72`
  - `SSO_RECHECK_MS = 3_600_000`
  - `SSO_WATCH_MS = 1_800_000`
  - `CLOCK_BACK_TOLERANCE_MS = 300_000`
  - `MIN_PIN = 6`, `MAX_PIN = 12`
  - `PIN_ATTEMPTS = 5`

- App tests: `./node_modules/.bin/vitest run --maxWorkers=3 --testTimeout=30000 <path>`.
- Typecheck: `./node_modules/.bin/tsc --noEmit -p tsconfig.node.json` and

## Review Focus

1. **The Keychain can't be read, or Touch ID's cache is stale, while Touch ID is the only factor.** The blob
   must be kept and the result must be `'unavailable'`. It must never be discarded (test in Task 3).
2. **A lock (screen, sleep) lands during the PIN scrypt.** The attempt is abandoned and not counted, as
   `verify` does with `epoch` today (test in Task 3).
3. **The Hub or Entra answers 500, 502 or 429, or times out, during the launch check.** The verdict is `grace`
   (within 72 h), never `needs-signin`, and the session is kept (test in Task 4).
4. **A PIN with a leading zero (`013579`), or a pasted PIN with spaces or letters.** `013579` unlocks. Input
   that isn't digits is rejected before any scrypt run with `'PIN must be 6-12 digits'`, and does not count as
   an attempt (test in Task 3).
5. **The Microsoft sign-in browser tab is closed, or the sign-in is cancelled, on the gate.** The gate returns
   to "Sign in with Microsoft", and Cancel is never disabled while waiting (test in Task 8).

### Task 5: `SsoGate`

**Files:**
- Create: `src/main/auth/sso-gate.ts`
- Test: `tests/main/sso-gate.test.ts` (new)

**Interfaces:**
- Consumes: `checkSession()` (Task 4); `HubConnection.status()`, `signIn()` and `signOut()`; the `sso_binding`
  table; the constants from Task 1.
- Produces:
  ```ts
  export interface SignInGate { verdict(): SsoVerdict; state(): SsoState; noteUnlocked(): void }
  export interface SsoHub { status(): HubStatus; checkSession(): Promise<SessionCheck>; signIn(): Promise<HubStatus>; signOut(): Promise<HubStatus> }
  export class SsoGate implements SignInGate {
    constructor(d: { db: Db; audit: Pick<AuditLog, 'append'>; hub: SsoHub; now: () => number })
    isBound(): boolean
    required(): boolean                       // isBound() || hub.status().linked
    check(opts?: { force?: boolean }): Promise<SsoVerdict>   // skips the network when verified < SSO_RECHECK_MS
    signIn(): Promise<SsoVerdict>             // interactive; maps a 403 HubError to 'blocked'
    bind(): void                              // from hub.status().user; throws 'sign in first'
    rebind(): Promise<void>                   // interactive sign-in, then rewrite oid, upn and hub_id
    unbind(): void
    onBlocked(fn: () => void): () => void
    watch(isUnlocked: () => boolean): () => void   // check({ force: true }) every SSO_WATCH_MS while unlocked
  }
  ```
- The verdict, per spec §1 and §2:
  - `required()` false → `'not-required'`.
  - The last check's result → `ok` with a matching `oid` and `hub_id` (or unbound) → `verified`, writing
    `last_verified_at`. A non-matching `oid` or `hub_id` → `mismatch`.
  - `offline` → `grace` when `now < last_verified_at + 72 h` and `now >= high_water_at - CLOCK_BACK_TOLERANCE_MS`.
    Otherwise `needs-signin`.
  - `expired` → `needs-signin`. `disabled` → `blocked`, and fires `onBlocked`.
  - Before any check in this process: `verified` if `last_verified_at` is within `SSO_RECHECK_MS`, else
    `needs-signin`.
  - `noteUnlocked()` raises `high_water_at` to `now`, and calls `bind()` when the gate is required but not bound
